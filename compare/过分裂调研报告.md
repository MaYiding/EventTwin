# 过分裂（该并未并）专项调研：根因实证 + 2024-2026 顶会方案地图 + 分级改进

> 2026-09-30。基线：两线对比报告中 v3.1 过分裂率 0.433 / v2 0.400（同实体+同类型+时间窗重叠的簇对中，Jev 判"应为同一事件"的比例）。本报告回答三个问题：过分裂到底死在哪一环？最近一年的顶会/工业界怎么解决？我们是结构缺陷还是小改动能救？

## 一、根因实证：判别层无责，死因全在上游

对 12 对"该并"簇对逐对回溯归类留痕（`compare/oversplit_autopsy_v31.json`，含决策表候选池、分数、排除原因、判别输出）：

| 死因 | 占比 | 含义 |
|---|---|---|
| **R1 召回未相遇** | 5/12 (42%) | 创建提及的候选池里根本没有对方簇——判别器从未见过它 |
| **R5 同日时间片隔离** | 5/12 (42%) | 两簇首成员同日发布，时间片快照互不可见（在线模拟固有）→ 各自新建 |
| R6 错并第三方 | 2/12 (17%) | 归并到了错误的三方簇（另一类问题，同 attach 精度问题） |
| R2 低分闸门直通新建 | **0** | 没有一对是"分数差一点没过 0.78" |
| R3 硬过滤误杀 | **0** | 没有一对被 distinct_sku/market/time_gap 排除 |
| R4 判别器判错 | **0** | 进入灰区的判定全部正确（与 attach 精度 1.000 互相印证） |

**R1 深挖（重要反转）**：5 对 R1 的两簇**事后实体交集全部非空**（享界G9、京东、上汽大众、全新ES8、小鹏P7+……）——结构化通道的原料本来就在，断点在三处结构性细节：
1. `structured_cluster_limit=50` **按行序截断**：hub 实体（小鹏汽车参与数百簇）的 participates_in 反查结果被截断，对方簇排在 50 名开外直接不可见；
2. 簇的实体边由**首报成员**带入：首报只绑定"蔚来"则"蔚来汽车"实体的提及查不到该簇（实体规范化未归一"蔚来/蔚来汽车"、"快手/快手科技"这类变体）；
3. 决策留痕只存 top10，事后审计无法区分"池里有但排 11+"与"池里没有"（可观测性问题，部分 R1 可能实为排序没顶上来）。

**结论一：换更强的判别器、调阈值、改硬过滤都对过分裂无效——Jev 见到候选时几乎全对，问题是它见不到。**这与两线过分裂持平（0.400 vs 0.433）完全自洽：v2/v3.1 只换了判别器，上游没变。

## 二、2024-2026 文献方案地图（按我们的根因对齐）

### 2.1 R5 的解法：二轮批处理合并（post-clustering optimization）——文献中的标准结构

**[Real-time News Story Identification（arXiv:2508.08272，2025-08）]** 与我们场景最像（在线新闻→故事簇）。关键实证：
- 明确诊断了我们的病："在线算法逐点处理、不知未来数据，宏簇合并阈值难以统一设定，**易过早产生多个本应同属一故事的簇**"（其图 5 正是同一摄影师故事被拆成关键词几乎相同的多簇）；
- 解法：**按天批次的 post-clustering optimization**——每日对已形成宏簇做重复合并（距离 < 阈值即并）；
- 关键发现：**用"主题词/命名实体的嵌入"做簇间合并判定显著优于簇中心嵌入**（AMI：主题词合并 0.569 vs 簇中心合并普遍 < 原始值）。我们的 `build_event_card`（类型+主体+对象+动作+时间+关键事实的规则模板卡）正是它说的"主题词卡"，且我们的卡已带 4096 维向量——**原料完全对齐，只差"合并这一步"**；
- 命名实体+时间窗（10 天）双条件合并；离群点显式检测（其数据 79% 故事仅 1 篇，与我们 94% 单成员簇同病，合并后 AMI 0.40→0.57）。

**[EDC: Extract-Define-Canonicalize（EMNLP 2024，arXiv:2404.03868，代码开源）]** post-hoc canonicalization pass 的模板：
- 一轮抽取完成后，向量检索 top-5 相似候选 + LLM 做**多项选择判定（MCQ，含 "None of the above" 兜底）**——与我们的 Jev choice（候选+none_of_them）协议完全同构；
- 双重验证（向量只出候选、LLM 做终判）避免 CESI 等纯聚类方案的过度泛化（CESI 把 place_of_birth/death 错聚一类，EDC 靠 LLM 否决）；
- 收益量化：精度损失 <3pt（0.982→0.956），换冗余组件数减半（529→200）+ 冗余度大降；
- 迭代终止：第二轮 refinement 边际收益 <0.5%（0.794→0.797），**一轮 merge pass 就够**。

**工业界实践（2025-2026）**：NewsCatcher（商业 News API 去重）、Insurge（embedding+向量库语义去重管线）、World Monitor（ACLED+GDELT 合并，元数据/Haversine 去重）——共同模式：**embedding 相似 → 聚类/社区检测 → 元数据辅助合并**，全是"在线粗分 + 批量精合"两层。

### 2.2 R1 的解法：blocking 召回修复

**[A Comprehensive Survey of Deep Learning for Entity Resolution（ACM Computing Surveys 2025）]** + **[Resource-efficient Blocking（Information Systems 2026）]**：
- ER 领域共识：**blocking（候选生成）的 recall 是整条管线 recall 的天花板**（"recall ceiling"）——与我们 R1 为最大死因完全一致；
- 趋势：embedding-based blocking（向量近邻）+ 多通道（键值倒排/元数据过滤）混合，单通道截断是主要损失源；
- 对我们的直接映射：`structured` 通道的行序截断 = 无排序 blocking，应改为**复合 blocking key**（实体×类型×时间窗）先过滤再排序截断。

**[CohTP（ACL 2026，本地 A01 已精读）]** 时间一致性 CDECR——注意它是**防误并**（时间不相交硬剪枝）的工作，与我们过分裂方向相反，但两个机制直接可用：
- **选择性 LLM 干预**：只对经诊断确认低质量的 32% 预测送 LLM 复判（全量干预反而 -3.7 分）——对应我们二轮合并只送"灰带簇对"给 Jev，不高置信全判；
- 其错误分析自证：27.8% 的真共指对被时间硬约束误杀——印证我们"未知不排除、只对明确不相容硬过滤"铁律的正确性（我们 R3=0 佐证）。

### 2.3 全局一致性：成对判定之后怎么安全地形成簇

**[Confidence-Guided Global Consistency in LLM-based ER（SBBD 2025）]**：
- 问题：成对 LLM 判定产生传递性不一致（A=B, B=C, A≠C）；现有方法只在局部解决；
- 解法：LLM 置信度做边权 → 加权 correlation clustering（ILP 精确解）修复不一致连通分量——42 个不一致分量全修复，仅删 52 条边且 98.1% 删对；
- 置信度信号有效：真匹配平均 0.936 vs 假匹配 0.729（MusicBrainz）——**Jev 的概率分布正是这种可分带的置信度**（我们评测：conf≥0.8 精度 96.8%）；
- 局限：ILP 不可扩展，作者自认近似算法是 future work——对我们：合并规模每批几十对，ILP/贪心都够用。

**[Adaptive Graph Refinement and Label Propagation with LLMs for ER（2026，arXiv:2605.25814）]**：图细化 + 标签传播 + LLM 判定的组合，correlation clustering 思想同上。

**[Cequel（CIKM 2025，本地 A06）]/[LeBoT（ACL 2026，本地 A05）]**：成本敏感的 LLM 聚类（预算内尽量少调 LLM）——对应我们"Jev p_same 先筛、灰带才送判"的分层思路已被文献验证为成本最优形态。

### 2.4 我们已有结构 vs 文献结构的对照

| 文献结构 | 我们现状 | 差距 |
|---|---|---|
| 在线微簇 + 按天批量宏簇合并（2508.08272） | 在线归类（时间片并行）+ **merge_clusters 仅人工** | **缺自动化二轮合并 pass**——结构缺一块，但缺口小（机制已有） |
| 主题词卡/命名实体引导簇间合并 | `build_event_card` 事件卡（+向量）已是主题词卡 | 原料齐备，只用于检索未用于合并 |
| 向量候选 + LLM MCQ 终判 + None 兜底（EDC） | Jev choice + none_of_them（完全同构） | 已具备 |
| 置信分带/选择性干预（CohTP/SBBD） | 评测已测出 conf≥0.8→96.8% 分带；high_confidence_bypass 先例 | 已具备，未用于合并 |
| 复合 blocking key 防截断损失（ER 综述） | structured 通道行序截断 LIMIT 50 | **需修** |
| 传递性保护（correlation clustering） | "A~B、B~C 不传递"铁律 + 簇间合并仅人工 | 铁律正确且必须保留；自动化合并需配高置信分带才不违反其精神 |

## 三、结论：结构缺陷还是小改动？

**判别层与整体六段主线结构没有缺陷**（R2/R3/R4 全零、attach 精度 1.0 是最强证据）。真正的缺陷是两个**具体、可修**的结构点：

1. **缺一个"二轮簇间合并 pass"**——这是文献公认的在线聚类标准组件（micro 在线分 + macro 批量合），我们只建了前一半。这不是推倒重来：`merge_clusters`（redirect+版本化+可撤销+人工操作）机制已在，事件卡+向量+Jev 判定原料全在，缺的只是"按天批次自动跑一遍簇对判定 + 高置信自动合 + 灰带进人工队列"的编排。
2. **召回通道的截断策略粗糙**（行序截断 + 实体变体未归一）——纯小改动。

## 四、分级改进方案

### 小改动（半天级，预计吃掉 R1 的大半）

| # | 改动 | 代码点 | 预期 |
|---|---|---|---|
| S1 | `structured` 通道改为复合 blocking key：先按（同类型 × 事件时间窗重叠）过滤，再按共享实体数降序排序，截断放宽到 100 | `recall.py` SQL 一处 | hub 实体不再淹没对方簇 |
| S2 | 实体归一补强：`entities.py` 规则表补"集团/科技/汽车后缀剥离已有一部分→再加产品线前缀归一（蔚来汽车→蔚来、快手科技→快手）"；或用 Jev 对高频实体做一次批量别名判定 | `entities.py` / seed 层级表 | 结构化通道相遇率提升 |
| S3 | 决策留痕 `candidates_json` 从 top10 扩到全池（或 top30） | `resolve.py _decision_row` | 可观测性，审计能区分"没召回"与"排 11+" |

### 中改动（1-2 天，**主攻方向**）：按天批次的簇间合并 pass

对齐 2508.08272 + EDC + SBBD 三篇的组合拳，全部用现成原料：

```
每时间片末（或每日批）：
1. 候选对生成（SQL，不受提及级 hub 截断影响）：
   活跃簇 × 活跃簇，条件：同 event_type + 共享实体 ≥1 + 事件时间窗重叠/间隔 ≤ hard_time_gap
   + 事件卡向量余弦 top（ann 初筛降规模）
2. Jev 判定（choice，对判）："簇甲与簇乙是否同一现实事件"（正是 C 维度评测的题面，
   我们已实测该题面 Jev 可用）
3. 分带执行（对齐评测 conf 分带与 CohTP 选择性干预）：
   - p ≥ 0.9  → 自动 merge_clusters（redirect+版本化+留痕，可撤销）
   - 0.5-0.9 → 进人工队列（Web 已有归类决策/CRUD 界面）
   - < 0.5   → 不动
4. 不传递闭包：合并只在"簇对"级判定，不做连通分量传递归并
   （保留铁律；如需全局一致性可加 SBBD 式删边校验，规模小用贪心即可）
```

预期收益（按根因分解）：
- R5（42%）：日尾批处理时两簇互相可见 → **基本全救**；
- R1（42%）：簇级候选生成用实体交集+类型+时间窗直接出对，绕开提及级截断 → **大半可救**；
- 精度风险：≥0.9 自动合并分带参照 attach 精度 1.0 与评测 conf≥0.8→96.8%，且 merge 可撤销；
- 综合预期：过分裂率 0.433 → **0.10-0.20**；同时单成员簇占比（94.4%）与多来源簇占比（5.6%）显著改善。

### 大改动（不建议现在做）

- correlation clustering 全局 ILP 优化（SBBD 作者自认扩展性是未解问题；我们的簇对规模用分带贪心已够）；
- micro/macro 两层流式重构（2508.08272 的 DBSTREAM/TextClust 路线，推翻现有时间片并行架构，收益不明确）；
- 训练式图精化（CohTP EA-GNN 类，需要标注数据与训练基建）。

## 五、执行建议

先做 S1-S3（半天，无风险），再做中改动的合并 pass（可先以"只报告不执行"的 dry-run 模式上线，用 C 维度同款评测验证合并候选的 precision，再放开 ≥0.9 自动合并）。验证闭环现成：重跑 `jev_judge.py` 维度 C 即可量化过分裂率变化。
